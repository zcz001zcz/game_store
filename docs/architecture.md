# Архитектура и гарантии

## Граница гарантии exactly-once

Сеть не позволяет гарантировать «ровно одну доставку сообщения». Здесь реализован
практический вариант: at-least-once доставка плюс exactly-once **эффект** внутри
домена. Его обеспечивают транзакции, блокировки строк и уникальные ограничения:

| Инвариант | Механизм |
| --- | --- |
| Один платёжный event | PK `payment_events.event_id` |
| Одна проводка capture на заказ | `UNIQUE (order_id, entry_type)` |
| Одна задача выдачи на заказ | `UNIQUE jobs.dedup_key` |
| Одна бизнес-выдача | `UNIQUE fulfillments.order_id` |
| Один код только одному заказу | уникальные `provider_stock.code`, `provider_issues.code`, `fulfillments.code` |
| Один результат запроса поставщику | `UNIQUE (provider, request_id)` |

Обработчик вебхука не вызывает поставщика. Он быстро записывает событие, меняет
заказ, создаёт проводку и ставит задачу в той же транзакции. Поэтому невозможна
ситуация «оплату закоммитили, а задачу потеряли».

## Состояния заказа

Основной путь:

`created → paid → delivering → delivered`

Сбой оплаты:

`created → payment_failed`

`paid` трактуется как монотонный факт. Это позволяет корректно пережить доставку
событий не по порядку: более поздно полученный `failed` не может отменить уже
подтверждённый платёж или выданный товар. Если до появления заказа пришли оба
события, они воспроизводятся по `created_at`, но `paid` всё равно имеет приоритет.

Восстановимые ветки:

- `delivering → out_of_stock → delivering → delivered`;
- `delivering → delivery_failed → delivering → delivered`.

`delivered` — окончательное состояние и не откатывается.

## Таймаут поставщика

У каждой пары «заказ + поставщик» ровно одна `delivery_attempt` и стабильный
`request_id`. Вызов выполняется вне транзакции БД, чтобы сетевой таймаут не держал
блокировку заказа.

Результаты разделены на две группы:

1. **Определённый отказ до выдачи** (`out_of_stock`, `unavailable_before_issue`).
   Только после такого ответа разрешён переход A → B.
2. **Неопределённый результат** (таймаут, оборванное соединение после отправки,
   невалидный ответ). Попытка помечается `uncertain`; задача повторяется с
   экспоненциальным backoff и тем же `request_id` у того же поставщика.

Заглушка сначала транзакционно резервирует ключ, а в режиме
`timeout_after_issue` задерживает уже ответ. Следующий запрос с тем же
`request_id` находит прежнюю выдачу и немедленно возвращает тот же ключ. Это
воспроизводит главную ловушку задания.

При восстановлении цепочка поставщиков тоже сохраняет этот инвариант: если у B
осталась неопределённая либо прерванная во время вызова попытка, прежний
определённый отказ A не сбрасывается.
Система сначала выясняет результат B с тем же `request_id` и не может снова
начать с A — иначе были бы возможны две внешние выдачи.

## Очередь без Redis

`jobs` — персистентная PostgreSQL-очередь. Worker атомарно выбирает доступную
задачу через `FOR UPDATE SKIP LOCKED`, увеличивает номер попытки и устанавливает
lease (`locked_at`, `locked_by`). Потерянная worker-процессом задача снова
становится доступной после `QUEUE_STALE_AFTER_SECONDS`.

Повтор использует экспоненциальный backoff с ограниченным jitter. После исчерпания
попыток задача переходит в `dead`, а заказ — в восстановимый `delivery_failed`.

Для текущего масштаба это уменьшает число компонентов и даёт атомарность с
бизнес-транзакцией. При росте очереди можно отделить outbox:

1. транзакционно писать события в PostgreSQL outbox;
2. публиковать их в Kafka/RabbitMQ;
3. оставить те же idempotency keys и ограничения у consumers.

## Ранний вебхук

Если `order_id` ещё неизвестен, событие сохраняется со статусом `pending`, и API
всё равно отвечает `200`. `POST /orders` допускает переданный клиентом `order_id`
для такого теста. В транзакции создания заказа pending-события блокируются и
применяются по порядку. Таким образом, раннее событие не теряется и не требует
гонки с периодическим poller.

## Каталог под нагрузкой

Каталог читает только активные товары и использует keyset pagination (`id >
after_id`), а не деградирующий `OFFSET`. Покрывающий индекс
`idx_products_active_catalog` содержит поля витрины. Остаток поставщика выбирается
по частичному индексу `(provider, sku, id) WHERE issued_at IS NULL`.

На тестовой выборке из 2000 SKU ожидаемый план — range/index scan по
`idx_products_active_catalog` от переданного `after_id` с остановкой после
`LIMIT`, а для каждой строки — индексный подсчёт доступных кодов через
`idx_provider_stock_available_by_sku`. В отличие от `OFFSET`, стоимость чтения
страницы не растёт линейно с её номером. План можно проверить на нужном
распределении данных командой:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT p.id, p.sku,
       (SELECT COUNT(*)
        FROM provider_stock ps
        WHERE ps.sku = p.sku AND ps.issued_at IS NULL) AS available_count
FROM products p
WHERE p.is_active = TRUE AND p.id > 1000
ORDER BY p.id ASC
LIMIT 100;
```

Для тысяч SKU этого достаточно. Следующие шаги при значительно большей нагрузке:

- read replica для каталога, master только для заказов/остатков;
- HTTP/CDN cache каталога с коротким TTL и инвалидацией по версии;
- предварительно агрегированный остаток по SKU, обновляемый событием выдачи;
- партиционирование `payment_events`, `jobs` и логических журналов по времени;
- `EXPLAIN (ANALYZE, BUFFERS)` на производственных распределениях данных, а не
  оптимизация по синтетическим догадкам.

Интеграционный Docker-runner транзакционно создаёт 2000 временных SKU с остатком,
после чего выполняет 50 одновременных запросов страниц по 100 товаров. Он проверяет
HTTP-ответ, принадлежность изолированной выборке, цену, остаток, строго возрастающий
`id` и курсор следующей страницы. Это воспроизводимая smoke/load-проверка
корректности, но не замена отдельному performance-тесту с целевым SLA и
производственным распределением данных.

## Наблюдаемость

API, worker и заглушки пишут JSON Lines в stdout/stderr. В записях присутствуют
`request_id`, `event_id`, `order_id`, `job_id`, `provider` и `request_id`
поставщика, но не печатается сам цифровой код.

Сверка показывает:

- оплаченные, но не выданные заказы;
- выданные без capture-проводки;
- расхождения суммы/валюты заказа и проводки;
- вебхуки, ожидающие появления заказа.
